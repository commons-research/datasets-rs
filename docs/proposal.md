# Proposal

## Question

Does collecting and adding structure to separate metabolomics datasets with rust increase interoperability and produce an actionable artifact for downstream use?

## Insights

This project should lead to:
1. Documentation of the current state of metabolomics datasets' interoperability
2. Fundamental aspects necessary to making a dataset interoperable
3. Challenges and existing problems with unifying datasets in an interoperable manner. 

Impact on Commons Lab: 
The positive impacts of this project on the lab research can be categorized as: 
*Downstream Application*: Having ready access to a diverse set of datasets, organized by features, could enhance projects that require access to datasets. Moreover, given the majority of the lab's code is currently being written in Rust, a crate makes importing the datasets for use through a standardized method simple and clear. This also enhances the interoperability of the datasets and would allow for downstream use and filtering. Moreover, moving the abstraction for commonly used datasets, such as LOTUS, COCONUT, PUBChEM, to an upstream crate would easy their import for use with the relevant data formats (in this example SMILES). Rather than as a convenience feature flag on a parser crate. 

*Dataset creation and dataset usage*: The project also has the potential to help shape how the lab chooses to collect and store datasets, as insights from this project offers insights into interoperability from a practical standpoint. The project has the potential to identify common pain points for dataset use, including access issues already discovered, such as dynamic dataset links based on versions. Moreover, the practical access to a wide set of datasets and a standard way to ingest a new dataset into the existing structure presented in this project, should offer cleaner ways to interact with these databases, discovery of other relevant databases that may otherwise have been overlooked, and as a result present a richer data analysis environment for lab research.

| Wilkinson et al., **“The FAIR Guiding Principles for scientific data management and stewardship,”** *Scientific Data*, 2016. [Nature](https://www.nature.com/articles/sdata201618) | Defines the FAIR principles of findability, accessibility, interoperability, and reusability, with an emphasis on making scientific data increasingly machine-actionable. | Provides the conceptual foundation for evaluating whether a shared representation and access layer improves the usability and interoperability of metabolomics datasets. | FAIR defines the desired properties of interoperable and reusable scientific data, but intentionally leaves domain-specific implementation and technical mechanisms unspecified. |
| van der Werf et al., **“Standard reporting requirements for biological samples in metabolomics experiments: microbial and in vitro biology experiments,”** *Metabolomics*, 2007. [Springer](https://link.springer.com/article/10.1007/s11306-007-0080-4) | Establishes metabolomics reporting requirements intended to improve the evaluation, comparison, and reinvestigation of experimental results. | Demonstrates that interoperability problems in metabolomics have long been recognized and that consistent representation of metadata is necessary for comparison and reuse. | Establishes reporting requirements for metabolomics experiments, but does not address programmatic acquisition or normalization of independently distributed datasets. |
| Hoffmann et al., **“mzTab-M: A Data Standard for Sharing Quantitative Results in Mass Spectrometry Metabolomics,”** *Analytical Chemistry*, 2019. [PubMed](https://pubmed.ncbi.nlm.nih.gov/30688441/) | Introduces a standardized format for exchanging quantitative mass-spectrometry metabolomics results using structured fields and controlled vocabulary. | Provides a concrete example of improving interoperability by imposing a common representation over otherwise heterogeneous metabolomics outputs. | Standardizes a particular class of metabolomics results, but does not provide discovery, acquisition, or a common access abstraction across heterogeneous external datasets and repositories. |
| Haug et al., **“MetaboLights: a resource evolving in response to the needs of its scientific community,”** *Nucleic Acids Research*, 2020. [OUP Academic](https://academic.oup.com/nar/article/48/D1/D440/5613675) | Describes a mature public metabolomics repository designed around metabolomics data, associated metadata, and community requirements. | Demonstrates the benefits of structured data and metadata within a domain-specific repository and provides an important source of metabolomics datasets for this project. | Provides interoperability within the MetaboLights ecosystem, but does not provide a common programmatic abstraction across independently maintained resources such as MetaboLights, Zenodo, PubChem, and COCONUT. |
| Sud et al., **“Metabolomics Workbench: An international repository for metabolomics data and metadata, metabolite standards, protocols, tutorials and training, and analysis tools,”** *Nucleic Acids Research*, 2016. [OUP Academic](https://academic.oup.com/nar/article/44/D1/D463/2502588) | Presents a public repository combining metabolomics datasets with metadata, standards, protocols, and analysis resources. | Provides another major example of repository-level organization and standardization of metabolomics data and illustrates the diversity of infrastructures with which downstream software may need to interact. | Standardization and access remain tied to a specific repository and data model rather than providing a common abstraction across independently designed metabolomics resources. |
| Wang et al., **“Sharing and community curation of mass spectrometry data with Global Natural Products Social Molecular Networking,”** *Nature Biotechnology*, 2016. [Nature](https://www.nature.com/articles/nbt.3597) | Demonstrates that shared infrastructure for MS/MS data can enable community curation, molecular networking, data reuse, and large-scale collaborative analysis. | Shows the downstream scientific value that can result when previously fragmented mass-spectrometry data become accessible through shared infrastructure. | GNPS primarily addresses sharing, analysis, and community curation within a mass-spectrometry ecosystem rather than general acquisition and programmatic interoperability across heterogeneous metabolomics datasets. |
| Jarmusch et al., **“ReDU: a framework to find and reanalyze public mass spectrometry data,”** *Nature Methods*, 2020. [Nature](https://www.nature.com/articles/s41592-020-0916-7) | Demonstrates that controlled metadata normalization across public mass-spectrometry datasets enables cross-study discovery, filtering, and repository-scale reanalysis. | Closely supports this project's premise that additional structure applied across independently produced datasets can create new downstream analytical capabilities. | ReDU focuses on harmonizing public mass-spectrometry data and metadata for search and reanalysis, but does not address whether heterogeneous metabolomics datasets more broadly can be represented and accessed through a reusable programming abstraction. |
| Akhtar et al., **“Croissant: A Metadata Format for ML-Ready Datasets,”** 2024. [arXiv](https://arxiv.org/abs/2403.19546) | Proposes a shared dataset description capable of representing metadata, resources, structure, and information required to load datasets across different tools and platforms. | Provides a useful cross-domain comparison for the idea that independently distributed datasets can become more interoperable when described through a common machine-readable abstraction. | Croissant is designed primarily around machine-learning datasets rather than metabolomics and does not address metabolomics-specific data types, repositories, metadata requirements, or scientific workflows. |

## Similar Projects

| Project | What to investigate | Why it matters to `metabolomics-datasets-rs` |
|---|---|---|
| **Hugging Face `datasets`** | Dataset registry, metadata, caching, remote/local loading, streaming, dataset cards | Required by Luca and one of the clearest examples of `load_dataset(...)` as a common abstraction. Current docs describe loading local/Hub datasets, caching and Arrow-based processing. [Hugging Face](https://huggingface.co/docs/datasets/main/en/index) |
| **TensorFlow Datasets** | Per-dataset builders, downloading/preparation, versions, citations, metadata | **Very close architectural precedent.** `DatasetBuilder` encapsulates downloading/preparing a dataset plus documentation/version/features. [TensorFlow](https://www.tensorflow.org/datasets/overview) |
| **Bioconductor ExperimentHub** | Curated resources + metadata + transparent local caching | Another very close precedent, but for scientific data rather than generic ML. Current release explicitly describes local cache management for reproducible data access. [Bioconductor](https://bioconductor.org/packages/release/bioc/html/ExperimentHub.html) |
| **OpenML** | Searchable dataset registry, stable dataset IDs, API-based acquisition | Demonstrates dataset discovery + metadata + programmatic retrieval. [OpenML](https://www.openml.org/apis) |
| **DataLad** | Distributed dataset acquisition/versioning/publication | Useful comparator for provenance and decentralized datasets rather than centralized hosting. [DataLad](https://docs.datalad.org/en/latest/index.html) |
| **DVC** | Dataset/artifact versioning, remote storage, reproducibility | Particularly relevant to your problem with changing upstream dataset versions and reproducibility. [Data Version Control](https://doc.dvc.org/user-guide) |
| **Frictionless Data** | Data packages, resources, schemas, validation, URL-based resources | Very relevant to your emerging `Dataset`/`DatasetArtifact` distinction; a Data Package is metadata plus one or more resources and can point at remote files. [Frictionless Framework](https://framework.frictionlessdata.io/docs/framework/package.html) |
| **Croissant** | Shared metadata vocabulary + resource/file structures + loading semantics | Probably the strongest metadata-interoperability comparator. [MLCommons](https://docs.mlcommons.org/croissant/) |
| **RO-Crate** | JSON-LD research-object packaging and linked metadata | Important because it approaches interoperability from the FAIR/semantic-web side rather than through a programming library. The current long-term release is RO-Crate 1.3. [researchobject.org](https://www.researchobject.org/ro-crate/specification) |
| **torchvision.datasets** | Built-in dataset classes, downloading/extraction and custom dataset abstractions | Simpler precedent showing how a language library can normalize acquisition of independently hosted datasets. [PyTorch Docs](https://docs.pytorch.org/vision/main/datasets.html) |
