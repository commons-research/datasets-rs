# Proposal: `metabolomics-datasets-rs`: Programmatic Interoperability for Heterogeneous Metabolomics Datasets

## Question

**What shared dataset-level properties and curation practices are required to provide a common programmatic interface for heterogeneous metabolomics datasets, enabling reusable downstream access while minimizing dataset-specific redesign?**

## Insights and Motivation

Public metabolomics and related chemical datasets are distributed through heterogeneous repositories, APIs, archives, file layouts, versions, metadata models, and licensing schemes. Individual resources may be well structured internally, but downstream software often requires dataset-specific knowledge simply to discover, acquire, identify, and prepare a dataset for use. This created duplicated acquisition logic across applications and makes it difficult to treat datasets as interchangeable scientific resources.

This project will develop and curate a collection of metabolomics and related scientific datasets behind a shared programmatic interface. Each curated dataset will describe its identity, scientific contents, source, and other relevant metadata while providing the logic necessary to acquire and materialize it for downstream use. Adding each new dataset therefore serves two purposes: it expands the practical utility of the library and tests whether the shared dataset model remains stable, which source-specific adaptations are necessary, and where generalization breaks down.

The project is expected to produce three principal scientific insights:

1. Characterization of current dataset-level interoperability: Which properties of publicly available metabolomics datasets are already sufficiently consistent to support shared programmatic treatment, and which remain specific to a repository or dataset?
2. Tested set of requirements for reusable dataset representation: Possible properties include stable identity, acquisition source, content, citation and licensing information, version/provenance information.
3. Empirical account of generalization limitations: Cases where a new dataset requires modification of the shared model, has difficulty being materialized in a reproducible manner, lacks metadata deemed necessary, or requires overly tailored structure will all be documented.

This project directly supports the data-modelling and validation axis of my broader PhD project. The doctoral research asks which shared structural constraints are sufficient to map heterogeneous experimental metabolomics datasets to reusable data models, without redesigning the model for each dataset. This project investigates an earlier dataset-level layer of that same problem: Datasets must first be identifiable, obtainable, described, versioned (when available), all before these heterogeneous experimental metabolomic datasets can be structurally or semantically integrated downstream. Ideally this process should be reproducible and reliable, while the metadata and provenance requirements may potentially inform later semantic-interoperability work.

### Impact on Commons Lab

**Downstream Application**: Common dataset acquisition layer that would remove dataset-specific fetching logic from lab crates performing analysis and parsing. Curated resources such as LOTUS and PubChem could be discovered and materialized through a common Rust API. Datasets would also be classified by the scientific content they provide, allowing downstream software to request, for example, all datasets containing SMILES, InChIs, MS/MS spectra, or combinations of these without needing to know where or how each dataset is hosted.

**Dataset Creation and Publication**: Through attempting to represent these datasets through one model should expose practical requirements for publishing reusable scientific datasets. These findings can inform how Commons Lab resources are released, including which identity, versioning, licensing, citation, provenance, and artifact information should be provided for reproducible downstream use.

Together, these works show that interoperability has been addressed at several levels: FAIR defines general objectives; metabolomics standards address reporting and exchange formats; repositories standardize resources within particular ecosystems; GNPS and ReDU demonstrate the scientific value of harmonization; and Croissant demonstrates a shared dataset-description approach in another computational domain. The remaining question addressed here is narrower: whether the acquisition and dataset-description layer itself can be generalized across independently maintained metabolomics resources, and which information is required for that abstraction to remain scientifically useful. As well as if a single representation is possible and practical.

## Expected Results

The expected engineering result is a curated Rust library that describes known metabolomics datasets, supports user-defined datasets, records relevant scientific and administrative metadata, materializes upstream resources locally, and exposes them through a consistent public API. Curated datasets will be classified according to the scientific content they provide, such as SMILES, InChIs, molecular formulae, MS/MS spectra, or other content types identified during development, allowing downstream applications to discover datasets appropriate to their requirements.

The software is not the sole research result though and will also record what must be added or changed as heterogeneous datasets with potentially different features are incorporated, thereby producing empirical evidence about the reusable and non-reusable aspects of dataset-level interoperability.

Three outputs are expected:

1. **Scientific Results**: Tested description of the dataset-level properties required for interoperable programmatic representation and acquisition.
2. **Engineering Artifact**: Open-source library with  public API for downstream use both in and out of the lab.
3. **Empirical Results**: A curated collection of real datasets integrated through the common interface, together with documented exceptions, missing metadata, source-specific requirements, and cases where generalization fails.

Evaluation will distinguish source-specific adaptation vs shared-model redesigns. Source-specific code for obtaining a Zenodo record, HTTP resource, dataset hosted on Hugging Face, or a study repository is expected. However repeated change4s to the conceptual `Dataset` model whenever a new dataset is introduced will likely indicate that the abstraction requires further generalization.

| Evaluation | Measurement | Evidence of success | Failure signal |
| --- | --- | --- | --- |
| **Model stability** | Changes to the shared dataset model as new pilot datasets are added | Later datasets can be incorporated primarily through source/layout adapters and existing metadata fields | Each dataset requires new public concepts or substantial redesign of the common model |
| **Acquisition/materialization** | Ability to reconstruct a usable local dataset from a clean environment | Selected public datasets can be reproducibly located and materialized through the same high-level API | Dynamic links, undocumented versions, authentication, or special cases make repeatable access unreliable |
| **Metadata coverage** | Availability and representation of source, content, license, citation, version/provenance, and artifact information | Available upstream information can be represented consistently and missing information is explicitly distinguishable from known values | Important scientific or reuse information must be discarded or encoded as unstructured special cases |
| **Dataset diversity** | Number and heterogeneity of supported sources, formats, scales, and scientific content | The model works across structure-centric, MS/MS, API-based, archive-based, and repository-hosted resources | The abstraction only works for datasets that are already structurally similar |
| **Downstream usability** | Use from at least one existing analysis/parser workflow | Multiple datasets can be supplied to downstream software without reimplementing their acquisition logic | Downstream consumers must still know how each dataset is hosted and fetched |

The project will be considered scientifically useful even if a fully general abstraction is not achieved. A negative result—for example, demonstrating that certain classes of metabolomics resources cannot share a meaningful dataset-level model without extensive bespoke behavior—would identify concrete limits to interoperability and provide evidence for how future datasets should be published.

A stronger failure would occur if the common model provides effectively no information beyond a name and download location, or if nearly every supported dataset requires a distinct public API. In that case, the proposed abstraction would not justify itself as an interoperability layer.

### Closest Comparative Projects

Conceptually Hugging Face's datasets, Bioconductor ExperimentHub, and Croissant appear to be the closest to this project.

Hugging Face datasets combines a large dataset catalogue with standardized discovery, metadata, downloading, caching, and loading through a common programming interface. This is conceptually close to the convenience and curation goals of this project. However, metabolomics and related scientific datasets hosted in the Hugging Face ecosystem are not consistently classified using domain-specific content categories, making targeted discovery difficult. metabolomics-datasets-rs instead curates a substantially narrower scientific domain and can therefore provide metabolomics-relevant classifications such as the availability of molecular structures, SMILES, InChIs, molecular formulae, or MS/MS spectra.

ExperimentHub combines resource metadata, programmatic retrieval, caching, and downstream scientific reuse. This project differs from ExperimentHub in that this project intends to describe datasets from multiple external infrastructures and while ExperimentHub has been written in R, this project will be written in Rust and integrable directly into downstream Rust based workflows.

Croissant offers a clear example of representation of datasets and separates datasets conceptually from files, resources, fields, licensing, and loading information. This project may look to Croissant for relevant ideas and differs from Croissant in that this project is metabolomics focused and through a smaller scope may be able to achieve clearer conclusions on the generalization of dataset representations in this field.

## Technologies

The project will be implemented in Rust, using explicit typed representations for dataset metadata, acquisition sources, and locally materialized artifacts. Rust is consistent with the broader doctoral methodology of investigating reliable scientific infrastructure and enables validation of many invariants through the type system while retaining the performance required for large scientific resources.

Initial acquisition mechanisms will include ordinary HTTP downloads and repository/API clients such as Zenodo. Additional source adapters will be added only when required by datasets selected for evaluation. Format-specific interpretation should remain in appropriate downstream libraries where possible.

Internet access is required for public repositories and APIs. The initial dataset set should not require privileged authentication, dedicated external servers, or software deployment within Zenodo, Hugging Face, GNPS, or other providers. Rate limits and provider usage policies will be respected. If future work requires restricted or proprietary resources, authentication and access-control requirements will be treated as a separate extension rather than assumed by the initial design.
